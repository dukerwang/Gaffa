# The Board: UI plan

Written 2026-10-24, after the Targets backend landed on `worktree-targets-board`.
The design is `docs/superpowers/specs/2026-09-22-transfer-board-design.md`. This
file is the build order, the code it touches, and what needs Duke's answer
before a line of UI is written.

## Where it stands

The backend is done and tested: the `player_targets` table, role levels, direct
visibility, the targets routes, matching, notifications and the route tests
(migrations 179 to 182, 1,024 tests passing, build passing). The live database
already holds all of it, with no rows. The October release shipped without it.

There is no Targets UI on this branch. An earlier UI exists on
`claude/inspiring-dewdney-fdb56c` (`TargetsClient`, `TargetRow`, `TargetEditor`,
about 2,000 lines). It predates the Board spec, and Duke retracted the cards
design it was built from (`docs/DECISIONS.md`, 2026-09-10), so it is reference
material only. Two pure helpers
from it came across because the Board needs them: `answerTarget` (can you
answer this target from your squad) and `demandLine` (what a listing's demand
reads as).

## Build order

**Step 0 has started: `/kit/board`.** On 2026-10-25 Duke asked for the design to
be rebuilt on the Gaffa Kit. The first cut is a public prototype page built
from real kit components (`Button`, `SegmentedControl`, `Select`, `MoneyStepper`,
`Checkbox`, `HoldButton`, `ResponsiveModal`, `toast`) and the app's own tokens,
phone first, with invented data and no route calls: the page layout (Wanted From
You, Your Targets, Your Listings, The Board) and the composer sheets (who, a
named target, a position, a listing, a listed player). It uses the shipped
section-head grammar, and every panel outline is a real border. Review it on
the branch preview at `/kit/board`. Because it is code, approving it means there
is nothing to port: step 2 moves it onto real data.

**Step 0 is a design pass, and it blocks step 2.** On 2026-10-24 Duke said
nothing about Targets is final: not the Board prototype, and so not the page
layout, the composer, or the tab name. The backend and step 1 don't depend on
any of that, so they can proceed. Steps 2 to 4 wait for a prototype Duke
approves, which is then ported as drawn.

Each step builds, passes tests and can ship alone.

1. **Domain code, no UI.** `src/lib/transfers/stance.ts` joins `listingStance`
   and `targetStance` in one module (they stay two functions, because the
   flags mean opposite things). `composerMode(player, myTeamId)` returns
   `listing | named | freeAgent | role`. `BoardPost` mapping in
   `buildTransfersModel`. `buildYourMove(model)`, a pure function over data the
   model already loads. Unit tests for all four. No visible change.
2. **The Board page.** `/transfers/board`: Your Listings, Your Targets, Wanted
   From You, then The Board with its Listed and Wanted switch and the position
   filter showing both counts. The section rule is `answerTarget`: if you can
   answer a target from your squad it sits under Wanted From You with buttons,
   otherwise on the Board with none. Built on the kit (`SegmentedControl`,
   `Select`, `Tabs`, `Skeleton`) and a `loading.tsx` skeleton. Ports the Board
   prototype as drawn, per Duke's rule on prototypes.
3. **`BoardComposer`.** The two-step composer from the spec: who, then the
   shared layout. Uses `MoneyStepper` for prices and the kit `ResponsiveModal`
   (a bottom sheet on a phone), `HoldButton` for Withdraw, and toasts. It calls
   the existing listings routes and the targets routes unchanged.
4. **Market gains Your Move.** One row per open decision (outbid, an offer
   waiting, a club wants your player, a target of yours is listed, a first bid
   on your listing), plus the board preview. Realtime on `player_targets`.
5. **Cleanup and docs.** Delete `ListingEditor` and `ListingsClient` once
   nothing imports them. Update `docs/USER_GUIDE.md` and `README.md` for
   Targets, role levels and direct visibility. Record the tab name in
   `docs/DECISIONS.md`.

## Checking it

The signed-in pages need a login, which is why UI bugs have reached Duke
instead of being caught. For each step, render the new components on a
temporary public test page with fixtures at phone and desktop widths, in both
themes, before pushing. Measure rather than eyeball: heights, overflow, and
truncation. Delete the page before committing.

Also: the RLS rule for direct targets tested in SQL against two accounts, not
through the UI; `npm test`, `npm run build`, `npm run check:ui`.

## Decisions for Duke

1. **Is the Board prototype final?** No (Duke, 2026-10-24: nothing with
   Targets is final). The Targets C canvas (2026-09-22) and the Market
   prototype (2026-09-23, on `docs/board-spec`) are the starting point, not the
   spec. What is still open needs naming before the design pass.
2. **The tab name.** "Board" is a placeholder (Duke, 2026-09-22). It can ship
   under that name and change later with one string.
3. **Redraft leagues.** They have no listings. Options: hide the Board
   entirely, or show it with Wanted and targets only. Targets could still help
   there (a manager says what they're after before a trade), but nothing lists
   against them.
4. **Caretaker clubs.** A Caretaker club has no manager to read a direct
   target. Proposal: direct targets aimed at a Caretaker's player notify
   nobody, and the target is simply visible on the Board to the league as
   public ones are.

## Risks

- `buildTransfersModel` is 902 lines and already the slowest read on the
  transfers pages. `BoardPost` must reuse what it loads, not add a query.
- Targets that follow a player when he changes clubs rely on the auto-fill
  trigger (`180`) and RLS reading `roster_entries` live. Test a trade and a
  free-agent signing end to end.
- `held` players: the composer must be disabled with the reason while a team
  is holding anyone, as the auction room is.
